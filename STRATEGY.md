# STRATEGY.md — Afterwords for macOS

What is irreversible in this repo, and what needs the owner's OK first.

Architecture, conventions, the scope freeze, and the release procedure live in
CLAUDE.md and RELEASING.md — this file does not repeat them. It records no
version numbers, counts, or "as of" dates: facts with an expiry turn into false
alarms, and a stale line here should never stop anyone's work.

## Get the owner's OK first

- **`git push origin main`** — `appcast.xml` on `main` *is* the production update
  feed (`SUFeedURL` points at `raw.githubusercontent.com/.../main/appcast.xml`),
  so a push offers whatever it contains to every existing install. `docs/`
  publishes the site the same way.
- **Tags, `gh release create/edit/delete`, `make release … PUBLISH=1`.**
- **Deleting a `release-manifest/*.sha256`** — the committed manifest is the only
  trusted SHA for a resumed release; the GitHub Release body is mutable and
  untrusted.

## Never

- **Run Sparkle's `generate_keys`, or print/export the EdDSA private key.**
  Overwriting it permanently bricks auto-update for every install.
- **Reuse or decrease `CFBundleVersion`**, even to roll back — supersede upward.
- **Hand-edit `appcast.xml`.** Sparkle silently rejects items whose `edSignature`
  or `length` don't match the published bytes, with no error surfaced anywhere.
  Go through `scripts/release_lib.py` / `make release`.
- **Hand-edit `project.pbxproj`** — it is regenerated by `make project` and your
  edits vanish. Edit `project.yml`.
- `git add -A` / `git add .` — the tree carries untracked evidence and WIP.

## Safe without asking

Reading anything; `make project/build/test/dmg`;
`python3 scripts/release_lib.py validate appcast.xml`; unit tests; patches on a
branch. A dry-run `make release VERSION=x` publishes nothing but does read the
signing key via `sign_update` — fine to run, worth mentioning in your report.
